# Локальная диагностика — 0.7.2+

При ошибке сначала вызовите `get_diagnostics({"errorsOnly":true,"limit":50})`. Инструмент работает без подключения плагина; для него нужен запущенный MCP. Для контекста начала/завершения операции используйте `errorsOnly:false`.

События содержат время UTC, уровень, название команды, `requestId`, длительность и сообщение/код ошибки, когда они доступны. `operation_started` и `operation_result` показывают ход операции; `TIMEOUT` с `outcome:unknown` означает, что сервер не знает результата. Это не отмена и не разрешение повторить изменение.

Если плагин завершит операцию после разрыва связи, его UI сохранит метаданные ответа до автоматического переподключения и отправит `plugin_late_result` с тем же `requestId`. Сам ответ и команда повторно не передаются. `plugin_completed` всё равно требует чтения изменённого узла. При закрытии окна плагина до отправки очереди эти сведения теряются; молчание журнала не доказывает отмену операции.

## Где читать

- Постоянный файл: `<packageRoot>/generated/logs/events.jsonl`. Фактический абсолютный путь возвращает `get_diagnostics.logFile`; packageRoot можно взять из `installation.json` скилла. Для обычной установки это `~/.codex/figma-local-mcp/generated/logs/events.jsonl`.
- Ротация: текущий файл и две предыдущие части `.1`, `.2`, примерно по 1 MiB. `get_diagnostics` читает и предыдущие части, сохраняя порядок. Обновление установки сохраняет каталог `generated` вместе с логами.
- В окне Figma-плагина: раскройте «Журнал событий и ошибок». Там последние 50 событий текущего запуска, включая потерю соединения и запоздалый ответ. Текст можно выделить и скопировать. Этот журнал не сохраняется при закрытии окна.
- Если запись на диск недоступна, `get_diagnostics.storageError` сообщает об этом и возвращает последние события из памяти. Ошибка логирования не прерывает работу с макетом.

Логи остаются на компьютере. Не записываются аргументы команд, результаты чтения макетов, изображения, имена файлов Figma или код сопряжения как отдельные поля. Из сообщений ошибок удаляются распознаваемые длинные секреты, URL и локальные пути. Сообщения Figma могут содержать короткие фрагменты названий/значений; маскирование не является гарантией удаления любого конфиденциального текста. Не публикуйте лог автоматически. Схемные ошибки, отклонённые самим MCP SDK до обработчика, и аварийное завершение процесса/плагина могут не попасть в журнал.

Не добавляйте содержимое макета в диагностические сообщения. После ошибки сначала сопоставьте события и прочитайте затронутые узлы; перезапуск используйте, когда операция завершилась или дальнейшая диагностика требует действий пользователя.

## Различение запусков и занятый порт (0.7.3+)

Новые записи содержат `pid` и случайный `sessionId` запуска сервера. Группируйте события по `sessionId`, а операции внутри запуска — по `requestId`. PID может повторно использоваться ОС; старые записи 0.7.2 этих полей не имеют. Одна ошибка, уже записанная мостом как `operation_result` или `operation_failed`, больше не дублируется событием `tool_failed`; ошибки до отправки команды по-прежнему записываются отдельно.

`server_start_failed` с `EADDRINUSE` означает, что новый сервер не занял порт. Это не доказывает отключение уже работающего сервера. Сначала проверьте `get_connection` и определите владельца порта, например на macOS: `lsof -nP -iTCP:3055 -sTCP:LISTEN`. Сопоставьте его PID с журналом и командой процесса. Не завершайте процесс по одному номеру порта и не запускайте дополнительные MCP для проверки подключения. Используйте уже подключённый клиент; завершать дублирующий клиент следует только после его идентификации и завершения активных операций. Если конфликтующий клиент неизвестен, сообщите об этом вместо догадки. Одновременная работа нескольких серверов на одном порту пока не поддерживается; автоматического присоединения второго MCP к первому нет.

В 0.7.4 таймаут по умолчанию — 120 секунд. Сервер сохраняет подключение и возвращает `operation: timed_out_waiting_result` до позднего ответа; новые команды изменения в это время отклоняются. При поступлении ответа пишется `plugin_late_result`, затем статус становится `idle`. При физическом разрыве соединения действует очередь диагностики UI, описанная выше.


## Проверка готовности и восстановление результата (0.7.5+)

Перед редактированием прочитайте версию из package.json используемого скилла и передайте её в get_connection как skillVersion. Это версия пакета (например, 0.7.5), а не номер публикации в каталоге. readiness перечисляет версии сервера, плагина и скилла, а также причину неготовности и действие для исправления. Без skillVersion поле skillVersionChecked=false: версия скилла не проверена. Несовпадение версий и отсутствие метаданных плагина блокируют новые изменения; диагностические чтения доступны.

Для новой записи возьмите nextOperationId из get_connection и передайте _operationId в инструмент изменения. Ответ содержит ID также в _meta.operationId. Повтор с тем же ID и аргументами возвращает сохранённый результат либо состояние ожидания/ошибки без повторного выполнения. Тот же ID с другими аргументами отклоняется. Для восстановления без повторного чтения локальных ресурсов предпочтителен get_operation({operationId}).

Состояния: running, waiting_result (тайм-аут), unknown (потеря связи), completed, failed. Ошибка failed может означать частично выполненное изменение: сначала осмотрите узлы. Новый ID не делает повтор безопасным. activeOperation в get_connection содержит команду и время ожидания. После переподключения того же окна плагина неподтверждённый результат отправляется повторно; сама команда не повторяется. Восстановление принадлежит той же сессии плагина и сервера.

Сервер хранит последние 100 записей и до 16 MiB результатов только в памяти. UI хранит до 32 неподтверждённых результатов и до 16 MiB по оценке длины строк UTF-16. После вытеснения записи или перезапуска сервера старый ID отклоняется, а не выполняется заново. Если результат недоступен, прочитайте затронутые узлы и решите, что действительно осталось сделать.

Кнопка «Скопировать отчёт» в плагине создаёт отдельный краткий отчёт: версии, состояние соединения/операции, время ожидания, код последней ошибки и типы последних событий. В него намеренно не включаются свободный текст ошибок, названия и ID объектов, аргументы, результаты, пути или ключи. При недоступности буфера обмена появляется выделенное поле для ручного копирования. Обычный подробный журнал остаётся локальным и может содержать фрагменты текста ошибок.

## Общий мост — 0.7.15+

Несколько MCP-процессов одной установки используют один мост и один открытый файл Figma. `get_connection.transport=shared` и `clientCount` показывают этот режим. События `shared_bridge_connected`, `mcp_client_connected` и `mcp_client_disconnected` штатные; отключение одного клиента не означает потерю связи остальных. Когда последний клиент отключился, мост завершается через три секунды. Порт 0 в проверках установки остаётся изолированным.

Мост допускает одну операцию Figma одновременно. Если другой клиент занял его или использовал тот же nextOperationId, прочитайте get_connection заново и проверьте файл перед новым изменением. Не повторяйте неопределённую запись с новым ID. История операций общая и хранится в памяти моста; get_operation доступен после закрытия отдельного клиента, пока жив мост. Перезапуск самого моста сбрасывает историю.

BRIDGE_VERSION_MISMATCH: закройте все старые MCP-клиенты, подождите несколько секунд и запустите обновлённые. Подключение кратко ждёт завершения старого моста, но не останавливает его принудительно. Начиная с 0.7.16 отклонённые подключения не сбрасывают таймер простоя. При переходе с 0.7.15 новая версия выдерживает паузу дольше трёх секунд перед повторной попыткой, чтобы старый мост успел завершиться. BRIDGE_AUTH_FAILED или BRIDGE_AUTH_TIMEOUT: проверьте владельца порта и установку. Это может быть другая установка, старая версия до 0.7.15 или посторонняя служба. Не меняйте ключ и не убивайте процесс только по номеру порта. При разрыве после отправки команды результат может быть неопределённым; автоматического повтора нет.

## Переменные и ошибки до записи (0.7.6+)

Привязка цвета или числового свойства сначала ищет переменную через `getLocalVariablesAsync` в текущем файле; список используется только внутри одной команды. Поиск по ID остаётся для уже доступных переменных библиотек, которых нет в локальном списке. `set_variable` изменяет только локальные переменные и получает коллекцию из локального списка.

`LOCAL_VARIABLES_UNAVAILABLE` означает, что Figma не вернула локальный список; `VARIABLE_LOOKUP_FAILED` — переменной в локальном списке нет и поиск по ID завершился ошибкой. Проверьте `get_design_system`, фактический ID и соединение самого приложения Figma. Подключённый локальный мост не доказывает доступность сервисов Figma. Не подменяйте запрошенную привязку обычным цветом молча.

`No properties changed` у `update_node` означает ошибку на этапе подготовки: запись ещё не начиналась, лишний шаг Undo не создаётся. Если ошибка возникла после начала записи, сохраняется предупреждение о возможном частичном изменении или результат отката простой фигуры. Сначала прочитайте статус операции и узел, затем решайте, нужна ли новая команда; не повторяйте старую вслепую.
