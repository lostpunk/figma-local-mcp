# Разработка и передача пакета

## Что редактировать

```text
figma-local-mcp/
  .codex-plugin/plugin.json    Метаданные пакета Codex
  .mcp.json                    MCP для установки как плагина
  src/                         MCP-инструменты, схемы и bridge
  plugin/                      Figma plugin: TypeScript + HTML + manifest
  skills/figma-local-design/   Инструкции, профили, примеры правил
  runtime/                     Собранный Node-сервер и лицензии зависимостей
  scripts/setup.mjs            Переносимая установка и генерация конфигурации
  scripts/package.py           Сборка ZIP из разрешённого списка файлов
  test/                        Проверки сервера, плагина и переносимости
```

Не правьте `runtime/server.mjs` или `plugin/code.js` вручную: они пересобираются. В проекте нет внешней службы, базы данных или обязательного API-ключа.

## Публичные тексты

Комментарии, описания релизов, коммитов и запросов на слияние должны описывать изменения и проверки этого проекта. Не добавляйте упоминания, ссылки, статусы или номера версий других каналов распространения. Применяйте правило и к ответам на комментарии.

## Как пересобрать

Для разработчика нужны Node.js 22+, npm и Python 3.9+. Из корня проекта:

```bash
npm ci
npm run release
```

`release` проверяет TypeScript, собирает плагин и сервер, запускает тесты, создаёт обе ZIP-сборки и каталог для публикации. В конце проверяет содержимое архивов, контрольные суммы, состав каталога и неизменность исходников после тестов:

```text
dist/figma-local-mcp-<version>.zip
dist/figma-local-mcp-<version>.zip.sha256
dist/figma-local-design-skill-<version>.zip
dist/figma-local-design-skill-<version>.zip.sha256
dist/skillstore/figma-local-design/
dist/release-<version>.json
```

JSON содержит версии, размеры и SHA256 архивов, а также хеши файлов исходников и каталога. В нём нет локальных путей, ключей или настроек. ZIP воспроизводимы при одинаковых входных файлах и окружении сборки: порядок, дата и права записей фиксированы. SHA256 проверяет целостность; это не цифровая подпись издателя. Для повторной проверки готовой сборки в том же checkout: `python3 scripts/package.py --verify`.

Получателю передавайте ZIP и при желании файл контрольной суммы. Архив уже включает `INSTALL.md`, `CUSTOMIZE.md` и исходники для дальнейших изменений. Ему не нужны `npm ci` и Python.

В ZIP не попадают `node_modules`, `generated`, `dist`, локальные регистрации клиента, коды подключения или домашние настройки. Упаковка использует явный список входных файлов и отклоняет симлинки. В `runtime/THIRD_PARTY_NOTICES.md` сохраняются лицензии зависимостей, которые действительно вошли в bundle. Не добавляйте пользовательские конфиги/токены в исходники или документы.

## Версии и проверки

Для нового релиза согласованно обновите package.json, обе записи версии в package-lock.json, .codex-plugin/plugin.json и skills/figma-local-design/version.json. Версия сервера и скомпилированного Figma-плагина берётся из package.json; копия package.json внутри скилла обновляется сборкой. Название архива берётся из package.json. Если меняются только внутренние правила команды, всё равно передайте новый архив и обновите установленные копии скилла.

Минимальные проверки перед передачей:

- `npm test`: поведение операций, ошибки, setup и запуск bundle из отдельной папки без node_modules.
- Запуск `scripts/package.py`, проверка состава ZIP и SHA256.
- Для изменений в Figma API/рендеринге: дополнительно открыть development plugin в настоящем Figma и проверить макет. Автотесты этого не заменяют.

При наличии системных навыков Codex можно дополнительно запустить `quick_validate.py` из skill-creator для папки скилла и `validate_plugin.py` из plugin-creator для корня пакета. Эти валидаторы не нужны получателю.

## Обновление локальной установки разработчика

После доработок запустите из исходного проекта:

```bash
npm run release:local
# Другая папка Codex, например для отдельной тестовой установки:
npm run release:local -- --codex-home /path/to/codex-home
```

Команда выполняет всю сборку и проверки, затем обновляет `<CODEX_HOME>/figma-local-mcp` и `<CODEX_HOME>/skills/figma-local-design` из одной проверенной версии. Без аргумента используется переменная CODEX_HOME или домашняя папка `.codex`. Обновление предназначено для уже установленного managed runtime и standalone-скилла, чей installation.json указывает на этот runtime. Иную установку команда отклоняет. Первичная установка и обычное обновление через install.mjs описаны в [INSTALL.md](INSTALL.md). Оба обновляющих сценария используют общий src/install-files.mjs; не вводите отдельную реализацию замены файлов. Получатель может проверить синхронизацию командой install.mjs --check.

До замены готовятся две временные копии. У каждой проверяются хеши; у runtime запускается MCP на свободном локальном порту, у сгенерированного плагина проверяется версия через имитацию Plugin API. Текущий файл Figma не затрагивается. Сохраняются ключ подключения, политика доступа к файлам, метаданные установленного скилла и дополнительные поля installation.json. config.toml команда не меняет. Даже при совпадении номера версии устанавливаются проверенные байты сборки.

Прежний runtime копируется в `<CODEX_HOME>/backups/figma-local-<version>-<suffix>/runtime`, прежний скилл переносится в `skill`; рядом лежит transaction.json. Файлы runtime заменяются атомарно по одному: его корневая папка, ключ, политика доступа и каталог логов остаются на месте, поэтому работающий сервер может продолжать писать журнал. Дополнительные локальные файлы сохраняются. При ошибке уже заменённые файлы восстанавливаются, новые удаляются, а прежняя папка скилла возвращается. Краткий локальный отчёт записывается в `artifacts/validation-<version>.json`. Отчёт и резервные копии не входят в архивы.

После успеха перезапустите Codex и Figma Local MCP Auto: уже запущенные процессы продолжают использовать старый код. Путь импортированного manifest остаётся прежним. В Windows открытые файлы могут помешать переименованию; остановите MCP/плагин и повторите команду из терминала.

### Если процесс был прерван

Откат обрабатывает обычные ошибки файловой системы. Принудительное завершение процесса или выключение компьютера между переименованиями требует проверки вручную:

1. Убедитесь, что процесс сборки/обновления завершён. Не удаляйте lock-файл работающего процесса.
2. Откройте последний transaction.json в резервных копиях; в нём указаны исходные, временные и резервные пути. `installed` означает успешную замену, `rolled_back` — завершённый откат; `prepared` или `runtime_updated` требуют сверить фактические файлы и папки. В новой схеме у runtime указана strategy: files и есть список runtimeFiles; у скилла — strategy: directory.
3. Для возврата остановите MCP и Figma-плагин. При strategy: files сначала сохраните аварийную копию текущего runtime, затем восстановите только файлы из списка runtimeFiles из backup/runtime. Если перечисленного файла не было в резервной копии, это новый файл — уберите его в аварийную копию. Сохраните текущие ключ, политику доступа и логи; они не входят в runtimeFiles. Для скилла и старых транзакций со сменой папок используйте следующий порядок. Для каждой существующей резервной папки сначала переименуйте её текущую папку `target` в отдельную аварийную копию, если она существует, затем верните резервную папку на этот путь из transaction.json. Используйте runtime и skill из одной транзакции. Если одной из резервных папок нет, оставьте соответствующую исходную папку на месте: она могла ещё не перемещаться. Не объединяйте файлы разных версий.
4. Только после восстановления удалите оставшийся `<CODEX_HOME>/.figma-local-update.lock` и/или `artifacts/release.lock`. Повторите сборку либо запустите восстановленную версию.

При неудаче автоматического отката временные файлы и lock сохраняются, а ошибка сообщает пути для восстановления. Резервные копии содержат локальные ключи — их нельзя передавать другим людям. Команды release и release:local ничего не публикуют; публикация выполняется отдельно по запросу пользователя.

## Два способа распространения

**ZIP + setup** — основной проверяемый путь, не требует marketplace. Установка описана в [INSTALL.md](INSTALL.md).

**Плагин в каталоге Codex** — комплект уже содержит `.codex-plugin/plugin.json`, скилл и `.mcp.json`. Можно включить его в поддерживаемый вашей командой каталог и проверить установку на целевой версии Codex. Конфигурация плагина использует `node ./runtime/server.mjs` с `cwd: "."`; разрешение пути относительно установленного корня зависит от поддержки локальных плагинов в клиенте. Если этот режим недоступен, standalone setup генерирует однозначные абсолютные пути. Установка в каталог и публикация в общий реестр не выполнялись.

Детали упаковки Codex: [официальная документация](https://developers.openai.com/plugins/build/plugins). Marketplace и публичная публикация — отдельные операции; наличие manifest не означает, что пакет опубликован или установлен другим пользователям.

## Доработка возможностей

### Регрессии обновления

`npm test` включает сценарии форматов установки v1/v2: ошибка посреди замены, откат, сохранение ключа, политики доступа, журнала, ID импортированного плагина и восстановление повреждённых файлов той же версии. Это проверки форматов установки с текущей сборкой, а не имитация старых исполняемых файлов путём смены номера версии.

Для проверки настоящей предыдущей версии распакуйте доверенный архив и выполните:

```sh
node scripts/check-upgrade.mjs --from /path/to/unpacked/figma-local-mcp
```

Сценарий создаёт временную установку из старых файлов, проверяет её, моделирует неудачное обновление и откат, затем обновляет до текущей сборки. Проверяет сохранность локального состояния, запускает изолированный MCP и проверяет восстановление файлов той же версии. Рабочая установка и открытая Figma не затрагиваются; временные папки удаляются. Команда не скачивает архивы и ничего не публикует. Для запуска сначала выполните `npm run build`. Та же матрица тестов выполняется в CI на трёх ОС; локальный запуск на одной ОС не подтверждает результаты остальных.

Добавляйте схему команды в `src/`, реализацию в `plugin/`, соответствующие MCP-аннотации и тесты. Сохраняйте работу через локальный Plugin API. Операции, которых нет в нём или которые требуют отдельного доступа, нельзя получить одной инструкцией в SKILL.md.

При передаче результатов проверок отделяйте фактически протестированное от предположений: в текущем окружении протестированы локальная сборка/протокол и имитация Plugin API; настоящий Figma Desktop и установка plugin bundle через UI требуют отдельной проверки.

Сборка копирует в скилл открытые runtime/, plugin/, src/ и setup-скрипты. Исполняемый код нельзя прятать в gzip, base64 или иной непрозрачный payload: проверяющий должен иметь возможность статически прочитать MCP-сервер и плагин. generated/ с локальными ключами в пакет не входит. scripts/package.py создаёт отдельный ZIP скилла из того же белого списка.
